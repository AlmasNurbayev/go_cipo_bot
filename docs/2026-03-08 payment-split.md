# Разбивка суммы чека по видам оплаты (наличные/карта)

## Контекст

В таблице `transactions` сумма чека хранится одним полем `sum_operation`, а тип оплаты — массивом `paymenttypes` (`0`=наличные, `1`=карта; при смешанной оплате оба значения). Для чеков с одним видом оплаты этого достаточно (сумма целиком относится к этому виду). Но при смешанной оплате (`paymenttypes = [0,1]`) было непонятно, сколько оплачено наличными, а сколько картой — эта информация не приходит в ответе по списку операций.

Она есть в ответе по конкретному чеку (`KofdGetCheck`, `internal/kofd_updater/api/kofdGetCheck.go`) — но не как структурированное поле, а как обычные строки печатной формы чека:
```
Төленген сома/Сумма оплаты            46 000,00₸
    Наличные:                         46 000,00₸
    Банковская карта:                    160,00₸
```
`kofd_updater` уже делает этот запрос для каждой транзакции — `KofdGetCheck` вызывается в `GetOperationsFromApi` (`internal/kofd_updater/kofd_updater_services/getOperations.go`), чтобы распарсить состав товаров через `utils.GetGoodsFromCheque`. Дополнительных запросов к API не потребовалось — текст чека (`chequeString`) уже был в памяти, доразобран для извлечения сумм по видам оплаты.

## Реализация

### 1. Миграция

`migrations/012_transactions_payment_split.{up,down}.sql` — колонки `sum_cash NUMERIC`, `sum_card NUMERIC` в `transactions`.

### 2. Модель

`internal/models/transactions.go` — поля `SumCash`, `SumCard null.Float` в `TransactionEntity`.

### 3. Парсинг

`internal/lib/utils/kofd_updater_utils.go` — функция `GetPaymentSplitFromCheque(data string, paymentTypes *[]int, sumOperation null.Float) (null.Float, null.Float, error)`.

Инвариант: там, где разбивка известна, `sum_cash + sum_card = sum_operation`, поэтому оба поля всегда заполняются вместе, в том числе при одиночной оплате:

- Один вид оплаты — разбивка не нужна: вся сумма идёт в соответствующее поле, а **противоположное явно записывается нулём** (не NULL), чтобы `sum_cash + sum_card` в SQL корректно давало `sum_operation`.
- Смешанная оплата (`len == 2`) — ищем в строках чека `"Наличные:"` и `"Банковская карта:"`, извлекаем суммы тем же приёмом, что и существующий `getTotalSum` (`:` → `₸` → `ParseStringToFloat`). Разбивка принимается только если найдены **обе** метки и `cash + card` сходится с `sum_operation` (допуск 0.01) — иначе она признаётся ненадёжной.
- Если метки не найдены или суммы не сходятся (другой формат чека) — возвращается ошибка; она **не критична**: вызывающий код логирует и оставляет `sum_cash`/`sum_card` = NULL, вставка транзакции не прерывается (в отличие от ошибки парсинга товаров, фатальной для продаж).

### 4. Оркестрация

`internal/kofd_updater/kofd_updater_services/getOperations.go` — в уже существующей горутине (после разбора товаров) вызывается `GetPaymentSplitFromCheque`, результат записывается в `listEntity[index].SumCash/SumCard`; ошибка только логируется, не прерывает вставку.

### 5. Хранение

`internal/storage/postgres/transactions.go`, `InsertTransactions` — добавлены `sum_cash`, `sum_card` в INSERT.

### 6. Аналитика бота

`internal/lib/utils/bot_utils.go`, `ConvertTransToTotal` (используется и `summary`, и `finance`) переписана на новую функцию `addPaymentSplit`, которая для каждой транзакции берёт суммы **напрямую из `sum_cash`/`sum_card`** — без ветвления по длине `paymenttypes`, так как теперь оба поля одинаково заполнены и при одиночной, и при смешанной оплате:

- `sum_cash`/`sum_card` оба валидны → идут в «нал»/«карта» напрямую (основной путь).
- иначе, если `paymenttypes` содержит один вид оплаты (старые операции до этой миграции, где `sum_cash`/`sum_card` ещё NULL) — сумма определяется по `paymenttypes`, как раньше.
- иначе (старая смешанная операция без разбивки) — вся сумма идёт в «смешанно».

Метка «смешанно» в выводе (`internal/botP/summary/handlers.go`) не менялась — меняются только суммы, которые в неё попадают, и для новых операций (после миграции) она фактически не должна использоваться.

## Вне рамок

Точечный вывод `sum_cash`/`sum_card` по каждому чеку не делался — везде, где выводится тип оплаты по одной транзакции (`GetTypePaymentText`, `internal/lib/utils/bot_utils.go:293`), продолжает использоваться только `paymenttypes`, без изменений:

- список чеков «Все чеки» (`getAllChecksService`, `internal/botP/summary/services.go:108`);
- текст одного чека (`internal/botP/summary/services.go:316`);
- уведомления о новых операциях через NATS (`internal/lib/utils/bot_utils.go:183`).

Для смешанной оплаты там по-прежнему будет пометка «Смешанно», хотя в БД (`sum_cash`/`sum_card`) и в аналитике по периоду (summary/finance, `ConvertTransToTotal`) сумма уже корректно разложена на нал/карту.

## Проверка

1. `go build ./...`, `make lint` — пройдено.
2. `make migrate_up` — применить миграцию.
3. `make updater1` (или `updater10`) — проверить в БД, что для смешанной оплаты (`paymenttypes = '{0,1}'`) заполнились `sum_cash`/`sum_card`, а для одиночных видов оплаты они равны `sum_operation`.
4. В логах проверять ошибки `"не удалось найти разбивку по видам оплаты в чеке"` — сверять с текстом чека (колонка `cheque`) на случай другого формата печати.
5. В боте (`/summary`, «итоги») за период со смешанными и старыми чеками — суммы новых операций должны попасть в «нал»/«карта», а «смешанно» — только для нераспознанных/старых.
